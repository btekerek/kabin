# ADR-005: Chat - Message model and the first Channels WebSocket

## Context

Every session type - guide, interpreters, listeners - needs a shared
text channel alongside the audio. Unlike everything built so far, chat
needs a server-initiated push: a listener shouldn't have to poll to see
a new message appear. `apps.realtime` (Django Channels) has been
scaffolded since the very first commit specifically for this moment and
has never been used until now.

## Decision

**Message model.** One table, not one per sender type. `sender_kind`
(`guide` / `interpreter` / `listener`) is the discriminator; `sender`
(nullable FK to `User`) is set for guide/interpreter senders,
`sender_listener_uuid` (nullable UUID) is set for listener senders -
exactly one of the two is populated, matching which anonymous-vs-real
identity model the rest of the app already uses per sender type.

**Who can send/read.** A new `IsSessionParticipant` permission: true if
you're the session's owning guide, an interpreter currently holding a
`ChannelInterpreter` claim on any of its channels, or a listener with a
`ListenerSession` row for it. This is "are you actually in this room
right now," reusing the membership tables ADR-002/003 already built
rather than inventing a separate chat-specific membership concept.

**REST is the only write path.** `POST /api/sessions/<id>/messages/`
creates the `Message` row and, in the same request, pushes it to the
channel layer group for that session so every connected WebSocket
client receives it immediately. The WebSocket connection itself is
receive-only from the client's perspective - there is no "send a chat
message" WS action. This keeps `ChatConsumer` deliberately minimal
(authenticate on connect, join a group, relay group messages to the
socket, leave the group on disconnect) and means there's exactly one
code path that can create a `Message`, not two that have to agree on
validation and authorization.

**WebSocket authentication.** Standard browsers and Flutter's web target
can't attach custom headers to a WebSocket handshake, so there's no
clean way to send a `Authorization: Bearer` header the way REST does.
Both credential types instead travel as query-string parameters on the
connection URL: `?token=<access token>` for guide/interpreter,
`?listener_uuid=<uuid>` for listeners. `ChatConsumer.connect()`
validates whichever is present (JWT signature + expiry via
simplejwt's `AccessToken`, or `ListenerSession` membership lookup for
the UUID case) and closes the connection immediately if it doesn't
check out - `IsSessionParticipant`'s REST logic, reapplied at connect
time since Channels has no equivalent of DRF permission classes.

Putting a bearer credential in a URL is a real tradeoff: query strings
can end up in server access logs, browser history, and proxy logs in
ways headers don't. The mitigation is the same one ADR-001 already
relies on for the access token generally - its 15 minute lifetime is
the whole blast radius. No new exposure window is created; the token
was already going to expire that fast regardless of transport.

## Alternatives considered

- **A `Ticket` model - REST issues a short-lived, single-use WS
  connection token, decoupled from the JWT.** More correct in the
  abstract (never puts the real access token in a URL at all), but it's
  a second auth system to build and test just for this one connection
  path. Revisit if the query-string exposure ever becomes a concrete
  problem rather than a theoretical one.
- **Let clients send chat messages over the WebSocket directly.**
  Rejected - see "REST is the only write path" above; two write paths
  means two places that have to independently enforce
  `IsSessionParticipant` and message validation, and they will drift.
- **Per-sender-type Message tables.** Rejected - chat rendering needs to
  interleave all three sender kinds in one ordered timeline anyway, so
  splitting storage would just require a union query to get back what a
  single table already gives for free.

## Consequences

- Every other real-time feature this project adds later (typing
  indicators, presence, live queue updates) can reuse `ChatConsumer`'s
  connect/auth pattern and the same `session-<id>` channel-layer group
  naming, rather than re-deriving WS auth from scratch.
- `channels-redis` (already a dependency) is what makes `group_send`
  actually fan out across multiple server processes in production; the
  in-memory channel layer (already the local/test default) is
  single-process only, which is fine for `pytest` but would silently
  drop cross-worker messages if `REDIS_URL` were ever unset in a real
  multi-process deployment. Worth a deploy-checklist item, not a code
  change.
- Testing this requires `pytest-asyncio` (already in
  `requirements-dev.txt` since the initial scaffold) and Channels'
  `WebsocketCommunicator` - the first async tests in this codebase.

## Amendment (2026-07-21): scoped general + per-channel chat, listeners removed

Listeners turned out not to need chat at all in practice, and a single
session-wide room didn't hold up once a channel could have multiple
interpreters relaying together. `Message` now has an optional `channel`
FK: null is a "general" message (guide + every interpreter in the
session, `IsSessionStaff`), set is scoped to just the interpreter(s)
holding a claim on that channel (`IsChannelInterpreter`) - the guide is
not a member of any individual channel's chat. `sender_listener_uuid`
and `SenderKind.LISTENER` are gone; every message now has a real
`sender`. `ChatConsumer` split into `SessionChatConsumer` (general,
`ws/sessions/<id>/chat/`) and `ChannelChatConsumer` (per-channel,
`ws/channels/<id>/chat/`), each with its own connect-time authorization
mirroring the REST permission it corresponds to.
